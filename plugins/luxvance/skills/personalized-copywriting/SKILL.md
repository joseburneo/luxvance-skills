# Personalized Copywriting

Takes a verified leads CSV plus a campaign template (V1 prompt + V2 prompt + rendered email) and produces a per-lead enriched CSV with `variable_1`, `variable_2`, normalized `company_name`, and (optional) `situation_line` / `value_line` / `cta_line`. Replaces Clay's Claygent step. Runs locally via Claude Code subagents.

## When to use

- A `verified.csv` from `enrich-and-verify-leads` is ready and the campaign template (from `build-campaign`) is locked.
- Jose wants per-lead variables generated without paying Clay per row.
- Re-running personalization on a subset (e.g. only the rows that failed QA).

## When NOT to use

- The CSV has not been verified yet — run `enrich-and-verify-leads` first. This skill assumes `is_sendable=true` rows only.
- The campaign template has not been built yet — run `build-campaign` first. This skill needs the V1 prompt, V2 prompt, and rendered email to know what to generate and how to render it for review.
- A single lead — just write the variables manually. The skill is built for batches of 100+.

## Inputs

1. **`verified.csv`** — output of `enrich-and-verify-leads`. Required columns: `email`, `first_name`, `last_name`, `company`, `job_title`, `industry`, `website`, `linkedin_url`. All rows assumed `is_sendable=true`.
2. **Campaign template** — three pieces from `build-campaign`:
   - Variable 1 prompt (block 6 of the kit) — includes the approved list.
   - Variable 2 prompt (block 7 of the kit) — includes the approved list.
   - Rendered email (block 3 of the kit) — used to show Jose a full render during the QA loop.

Inputs can be passed as file paths or as conversation context (paste the block text). The skill accepts either.

## Outputs

**`enriched_leads.csv`** — matches the schema in `launch-instantly-campaign/references/leads-csv-schema.md`.

Required columns:

|---|---|---|
| `email` | verified.csv | Pass-through. |
| `first_name` | verified.csv | Capitalized, whitespace stripped. |
| `last_name` | verified.csv | Capitalized, whitespace stripped. |
| `company_name` | normalized from `verified.csv.company` | See company-name normalization rules below. |

Optional columns (include only if present in inputs):

|---|---|---|

        │

## Phase 1: Inputs check

Confirm the inputs are usable before starting any subagent work.

Checks:

1. `verified.csv` exists and is readable.
2. Required columns present: `email`, `first_name`, `last_name`, `company`.
3. Total row count is 50 or more. (Below 50, the iterative QA loop is wasteful — just generate manually.)
4. V1 prompt and V2 prompt are available (file path or pasted in conversation).
5. Rendered email is available (block 3 of the kit).

**Check for a saved tuned prompt for this client.** If `profiles/<client-slug>/personalization-prompt.txt` exists, ask:

> Found a saved personalization prompt for [client] from [date]. Use it (default) or re-tune from scratch?

If Jose says "use it", load the saved prompt and SKIP the iterative QA loop (Phase 4) — go directly to Phase 5 with the saved prompt. If Jose says "re-tune", run the full QA loop and OVERWRITE the saved prompt at the end of Phase 4.

The saved-prompt path means: on the second and subsequent campaigns for the same client, personalization is faster because the V1/V2 framework has already converged. This is the "save tuned prompt for reuse" pattern from GEX `personalization-subagent-pattern`.

If any other check fails, report it to Jose plainly and stop.

## Phase 4: Iterative QA loop

This is the centerpiece. Jose's specific request: before running 2,500 leads through a subagent, validate the prompt produces good variables on 30 sample leads in three rounds of 10.

### Loop mechanics

For each of the 3 rounds:

1. Pick 10 leads at random from `verified.csv` (different 10 each round, no repeats).
2. Run **one** subagent over those 10 leads with the V1 prompt and V2 prompt.
3. For each lead, render the full email (subject + body, all `{{firstName}}`, `{{companyName}}`, `{{Variable 1}}`, `{{Variable 2}}` substituted). Pick one variant from each `{{RANDOM|...}}` block to keep the render readable.
4. Show Jose the 10 rendered emails in a single message. Format:

```
### Sample 1 of 10
Lead: [first_name] [last_name], [job_title] at [company_name] ([company_domain])
V1: "[generated variable_1]"
V2: "[generated variable_2]"

Subject: [rendered subject]
Body:
[rendered body]

---
```

5. Wait for Jose's feedback. Possible responses:
   - **"OK"** or **"good"** → proceed to next round.
   - **"tune [aspect]"** or **"V1 should be more X"** → adjust the V1 or V2 prompt inline (modify the approved list, add a constraint, change a rule), re-run the same 10 leads, show again. Do not start a new round until Jose approves.
   - **"drop [N]"** → flag that lead for the QA pass to handle.

6. After 3 rounds of OK, proceed to Phase 5.

### Save the tuned prompt (after Phase 4 converges)

When the QA loop completes (3 consecutive rounds with zero corrections OR Jose says "lock it"), save the final tuned V1 prompt + V2 prompt to:

```
profiles/<client-slug>/personalization-prompt.txt
```

Format:

```
# Tuned personalization prompt for <client>
# Last tuned: <YYYY-MM-DD>
# Rounds to convergence: <N>
# Final batch size: 10
# Campaigns this prompt has shipped: <list of campaign IDs>

## Variable 1 prompt (final)
<verbatim V1 prompt + approved list>

## Variable 2 prompt (final)
<verbatim V2 prompt + approved list>

## Per-lead rules adopted during tuning
- <any new rule Jose added during the loop>
- ...
```

Also append a metadata entry to `profiles/<client-slug>/client-profile.yaml` (create the file if it does not exist):

```yaml
personalization_prompt:
  path: profiles/<client-slug>/personalization-prompt.txt
  last_tuned: <YYYY-MM-DD>
  rounds_to_convergence: <N>
  campaigns_using_this_prompt:
    - <campaign-slug>
```

On the next campaign for the same client, Phase 1 detects this file and offers the "use saved prompt or re-tune" choice — skipping Phase 4 entirely when the prompt is still good. This is how Luxvance compounds: each client's V1/V2 framework only gets tuned once (per ICP shift), not every campaign.

### Subagent prompt for the QA-loop rounds

See `references/subagent-prompt.md` for the full template. The subagent receives:

- The V1 prompt (from the kit, verbatim).
- The V2 prompt (from the kit, verbatim).
- The list of 10 leads (`email`, `first_name`, `last_name`, `job_title`, `company`, `industry`, `website`, `linkedin_url`).
- The Variable rules (see below) appended as hard constraints.

### Hard variable rules (must appear in every subagent prompt)

Critical lessons from the 2026-05-17 session. Bake these into the subagent prompt every time:

1. **Variable 1 must NEVER echo the lead's own role.** If the lead is a Sales Director, V1 must NOT be "Sales Directors at X". They would be talking about themselves. Pick a different buyer persona (e.g. CEO, CFO, COO, CIO, CMO, CHRO, CRO depending on the offer).
2. **Variable 2 brand size must match Variable 1's size descriptor.** Mid-market V1 → mid-market brands. Enterprise V1 → enterprise brands. Growing companies V1 → growing brands. Mismatched sizes break credibility.
3. **2-8 words per variable.** Lowercase. No trailing punctuation. No em-dashes.
4. **Source field:** only the LinkedIn company description and job title. No web search.
5. **Approved list first.** If a phrase from the approved list fits, use it verbatim. Only invent a new phrase when nothing in the list maps cleanly.
6. **Safe fallback for ambiguous cases.** If the lead's industry is genuinely unclear, return the documented fallback string from the V1 / V2 prompt (e.g. "growth-stage businesses").

### Few-shot examples (Jose's actual patterns)

Embed these in the subagent prompt as positive examples:

```
Lead: Business Director at Gleeson Recruitment (staffing)
  → V1: "General Managers at growing companies"
  → V2: "Jaguar Land Rover, Rolls-Royce, and John Lewis"

Lead: VP Sales EMEA at ThinkAnalytics (media analytics)
  → V1: "Heads of Revenue at enterprise companies"
  → V2: "Sky, ITV, and Channel 4"

Lead: Business Director at IDEX Consulting (insurance)
  → V1: "Chief People Officers at insurance carriers"
  → V2: "Aviva, AXA UK, and Zurich Insurance Group"

Lead: BD Director at IFS assyst (ITSM software)
  → V1: "CIOs at enterprise companies"
  → V2: "Tesco, Vodafone, and Unilever"

Lead: Sales Director at Black&Callow (legal/IPO services)
  → V1: "CEOs at enterprise companies"
  → V2: "Aviva, HSBC, and Legal & General"
```

### Bad examples (what to avoid)

Embed these in the subagent prompt as negative examples:

```
BAD: Lead is Sales Director → V1: "Sales Directors at SaaS companies"
     (Echoes the lead's own role. They will say "yes, I am one." Use a different buyer.)

BAD: V1: "Mid-market SaaS founders" + V2: "Salesforce, Microsoft, and Oracle"
     (V2 brands are enterprise. Mismatched scale. Use mid-market named brands.)

BAD: V1: "B2B Software" (2 words, all caps)
     (Capitalization. Must be lowercase: "b2b software firms".)
```

## Phase 5: Full batch

After 30 leads with Jose's OK, run the full remaining batch.

Mechanics:

1. Split the remaining `verified.csv` rows into 3 equal batches (typical: 800-1,000 leads each).
2. Spawn 3 Sonnet subagents in parallel via the `Agent` tool (`subagent_type: general-purpose` since we need write access to JSON files).
3. Each subagent receives:
   - The (possibly tuned) V1 prompt.
   - The (possibly tuned) V2 prompt.
   - Its slice of leads as a JSON array.
   - The hard variable rules.
   - Few-shot examples.
   - Output instructions: write a JSON file at a known path (e.g. `/tmp/enriched_batch_N.json`) with the structure:

```json
[
  {
    "email": "...",
    "first_name": "...",
    "last_name": "...",
    "company_name": "...",   // normalized
    "company_domain": "...",
    "title": "...",
    "linkedin_url": "...",
    "variable_1": "...",
    "variable_2": "..."
  },
  ...
]
```

4. Wait for all 3 subagents to finish. Each returns a summary; the actual data is in the JSON files.
5. Concatenate the JSON files into a single in-memory list.

If a subagent fails, report the failure to Jose and offer to re-run just that batch.

### Company name normalization (applied inline by the subagent)

Rules — bake these into the subagent prompt:

1. Strip legal suffixes: `LTD`, `LIMITED`, `LLC`, `INC`, `INC.`, `PLC`, `CORP`, `CORP.`, `GMBH`, `SA`, `S.A.`, `B.V.`, `BV`. Case-insensitive match.
2. Fix `ALL CAPS` company names to Title Case: `JAGUAR LAND ROVER` → `Jaguar Land Rover`.
3. Preserve **intentional lowercase brands**: `iPhone`, `ThinkAnalytics`, `Black&Callow`, `IFS assyst`. If the original casing is mixed and intentional (uppercase letter in middle of word), leave it alone.
4. Strip trailing punctuation, double spaces, and surrounding quotes.
5. If `company` is empty or null, fall back to the email domain (capitalized).

See `references/company-name-normalization.md` for edge cases.

## Phase 6: QA pass

After the full batch is in memory, spawn 3 more Sonnet subagents in parallel via the `Agent` tool. Each receives one third of the enriched leads.

Each subagent's job: for each lead, output `keep`, `fix`, or `drop`.

### Drop criteria

- Charities, non-profits, NGOs.
- Government agencies, ministries, public sector.
- Education institutions (universities, schools).
- Lead's company is clearly out of scope for the campaign (wrong industry, wrong size).
- Lead's `company_name` after normalization is unreadable garbage (e.g. domain with no company info).
- Variable 1 or Variable 2 is empty or violates the hard rules.

Typical drop rate: 2-4%.

### Fix criteria

- Variable 1 echoes the lead's own role → regenerate with a different buyer persona.
- Variable 2 brand size mismatches V1 → regenerate with size-matched brands.
- Company name normalization missed a legal suffix.
- Variable contains an em-dash or trailing punctuation.

### Output schema per lead

```json
{
  "email": "...",
  "action": "keep" | "fix" | "drop",
  "reason": "[one-line reason if fix or drop]",
  "fixed": {                          // only present if action="fix"
    "variable_1": "...",              // corrected value
    "variable_2": "...",
    "company_name": "..."
  }
}
```

Concatenate the QA output. Apply the fixes to the in-memory list. Drop the drops. Surface the drop count and the top 3-5 fix reasons to Jose ("47 dropped: 12 charities, 18 gov, 17 out-of-scope. 89 fixed: 34 V1-echoed-role, 41 V2-size-mismatch, 14 normalization").

## Important rules

- **Do not write copy.** That is `build-campaign`. This skill only generates per-lead variables and normalizes names.
- **Do not skip the iterative QA loop** even when Jose says "just run it". The 30-lead validation has caught prompt errors that would have wasted 2,500 lead generations. If Jose insists, fine — but flag the risk explicitly first.
- **Do not call the OpenAI API without `OPENAI_API_KEY` from `credentials/master.env`.** Read the key with the Python `with open()` pattern documented in [SESSION_HANDOFF_2026-05-17.md](../../../docs/SESSION_HANDOFF_2026-05-17.md), not via `grep` or `os.environ` (gitignore blocks reads on master.env, and the env var is not auto-loaded).
- **Do not let any column outside the schema leak into the output.** Schema is the contract. The deployer rejects unknown columns.
- **Default to Sonnet.** Opus is for the rare case where Jose says "máxima calidad". OpenAI is for A/B comparison, not the primary path.
- **One subagent per batch, not one per lead.** Per-lead subagents are 100x more expensive and slower. A subagent can process 800-1,000 leads in one prompt.

## Language

Default to the language of Jose's most recent message for all user-facing prompts (cost estimates, QA-loop reviews, summary at the end). Subagent prompts and the few-shot examples stay in English because the LinkedIn descriptions and approved lists are in English.
